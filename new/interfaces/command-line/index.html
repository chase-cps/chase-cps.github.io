Command line#

The Python package installs the chase-cps command, with the commands check, repair, view, export, install, and doctor.

In the options, a contract is NAME, or NAME+NAME+... for the composition of the contracts. A model is a state machine in an SMV file, or in a JSON file (a state machine, or a controller of slugs synthesized from the contract).

Checking a specification#

chase-cps check checks the contracts of a specification file in the logics language of CHASE, or of a JSON file (one contract, a list of contracts, or {"contracts": [...]}, each in the format of Contract.from_dict), and prints the counterexamples.

Usage

chase-cps check FILE [options]

Parameters:

Contract-based verification (nuXmv):

  • --verify The assumptions and the guarantees can hold together (A ∧ G satisfiable). It is the default when no check is given.
  • --compatible Some environment satisfies the assumptions.
  • --consistent Some behavior satisfies A → G.
  • --contracts C... The contracts checked by the three options above (default: all).
  • --refines R A R refines A. It may be repeated.
  • --implementation MODEL C The model is an implementation of C.
  • --environment MODEL C The behaviors of the model satisfy the assumptions of C.
  • --receptive MODEL C The model accepts every input that the assumptions of C allow.

GR(1) synthesis (slugs):

  • --realizable C C is realizable. It may be repeated.
  • --synthesize C Synthesizes a controller for C. It may be repeated.
  • --well-separated C The component cannot win by forcing the environment to violate its assumptions.
  • --vacuous C The component can win without an output that a liveness guarantee asks for.

For every check:

  • --core When a check fails, gives a minimal set of terms that explains it.
  • --json Prints the results as JSON.
  • --timeout S Seconds for each check.
  • --backend auto|nuxmv|nusmv The model checker.
  • --engine auto|ic3|bdd|bmc|portfolio The engine of the model checker.

Continuous time (a step is a sample):

  • --period S The time between two steps. The intervals may then be written with times: G[0s,2s], F[0ms,500ms].
  • --lipschitz VAR=RATE... How fast each variable changes, per second (or one RATE for every variable). --refines then holds in continuous time, between the samples too (sampled signals).

For instance:

$> chase-cps check specs.ltl                                    # verify every contract
$> chase-cps check specs.ltl --refines Joint1+Joint2 Joints      # the composition refines Joints
$> chase-cps check specs.ltl --realizable Joint1 --json
$> chase-cps check specs.ltl --implementation joint1.smv Joint1 --receptive joint1.smv Joint1
$> chase-cps check plant.ltl --period 0.1 --lipschitz x=2 --refines Plant Req

The exit status is 0 when every check passes, 1 when a check fails or does not finish, and 2 on an error in the input.

Drawing a specification#

chase-cps view writes the diagram of a file as a web page. The file is a specification in the logics language, in JSON, or in SystemVerilog Assertions (.sv), or a Verilog module (.v, or .sv without assertions), drawn with its state machine.

Usage

chase-cps view FILE [options]

Parameters:

What is drawn:

  • --contracts C... The contracts drawn. By default, all the contracts of the file, but those drawn inside another box.
  • --refines R A Draws R inside A. It may be repeated.
  • --implementation MODEL C Draws C as a component with its model: SMV, JSON, or RTL read with Yosys (FILE:MODULE for a file with several modules). It may be repeated.
  • --environment MODEL C Draws the model as an environment of C, on its left. It may be repeated.
  • --open C... Draws these contracts open: their terms, and the core of a check that fails.

The checks:

  • --check Checks that the assumptions and the guarantees of each contract can hold together (A∧G, with the core when they cannot), and the refinements, the implementations, and the environments drawn (nuXmv or NuSMV).
  • --verify Checks that each contract drawn is compatible and consistent.
  • --realizable Checks that each contract drawn is realizable (slugs); when it is not, marks the guarantees of the core.
  • --timeout S Seconds for each check.
  • --budget S No check starts after S seconds; the checks left are not marked.
  • --results FILE Where the results of --check are kept (default: next to the file, charger.ltl → charger.results.json). A check of contracts that have not changed is read from it, not run again.
  • --no-results Keeps no results.
  • --no-checks Leaves the three checks above out.

The page:

  • -o PAGE The page written (default: FILE with .html).
  • --format html|json The page, or the data of the diagram.
  • --elk PATH Puts a local elk.bundled.js in the page, which then works offline (default: ELK from a CDN).
  • --serve Serves the page on this computer, and draws it again whenever the file changes. When the file cannot be drawn, the page keeps the last diagram and says why. The repairs of the page run there, and Apply writes the values into the file (Diagrams).
  • --host HOST, --port PORT Where the page is served.

For instance:

$> chase-cps view specs.ltl                                       # writes specs.html
$> chase-cps view specs.ltl --refines Joint1+Joint2+Joint3 Joints --check --realizable
$> chase-cps view specs.ltl --open Joints --serve                 # drawn again on each change
$> chase-cps view arbiter.v                                       # the module and its states

Without --refines and --contracts, the contracts are put together by their ports:

  • an output and an input with the same name are wired;
  • contracts with the same inputs and outputs are versions of one part (fixes, or candidates): the first one in the file is wired, the others are drawn apart;
  • a contract whose outputs are driven by several parts, which read from outside only its inputs, is the contract of their composition: the parts are drawn inside it, and --check checks the refinement;
  • when two parts or more are written but some outputs of the contract are driven by none, the part not written yet is drawn as a hole: the quotient of the contract by the parts.

The options can also be written at the top of the file, in comments (// view: in Verilog). The files named there are taken from the folder of the file:

# view: --implementation models/arb.json Arb --check --open Arb
CONTRACT Arb ...

Repairing and exporting#

chase-cps repair FILE takes the checks of chase-cps check and --param NAME=LOW..HIGH (:int for an integer), and finds the values of the constants that make the check pass (Repair).

chase-cps export FILE --to smv|smt|gr1|sva|c|spec|json writes a check, or the contracts, as the input of a tool you run yourself: nuXmv or NuSMV (smv), z3 or cvc5 (smt), slugs or gr1c (gr1), an SVA checker, ESBMC or CBMC (c).

Installing the tools#

chase-cps install nuxmv|nusmv|slugs|esbmc installs a tool into ~/.chase, and chase-cps doctor lists the tools found and how to install the others (Installation).
